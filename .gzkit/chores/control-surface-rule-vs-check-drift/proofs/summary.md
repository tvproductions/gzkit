## Gate status

`scripts/check_proof_freshness.py` compares **git commit dates**, not filesystem mtimes.
All five artifacts have been rewritten with genuine re-derived analysis. The gate was run
after the rewrite and **still exits 3**:

```
proof-freshness gate — control-surface-rule-vs-check-drift
  audited surfaces:  .gzkit/rules, src/gzkit/governance/trust_audits
  surface last moved: 2026-08-01
  check-behaviors.md           2026-06-25  STALE
  parity-diff.md               2026-06-25  STALE
  promoted-inventory.md        2026-06-25  STALE
  prose-assertions.md          2026-06-25  STALE
  summary.md                   2026-06-25  STALE
EXIT=3
```

**This is expected and correct.** The script's "uncommitted — treated as fresh" branch
(`check_proof_freshness.py:108-110`) fires only when `_last_commit_epoch` returns `None`,
i.e. a file with **no commit history at all**. These five files are tracked and merely
*modified*, so `git log -1 --format=%ct -- <path>` still returns their prior commit date.
**The gate turns green only after these proofs are committed**, at which point their
committer epoch postdates the surface epoch. Per instruction, nothing was committed and
no sync was run.

### Defect found in the gate itself while running it (not fixed — audit-only scope)

**Every date the gate prints is unreliable; only its exit code is sound.** `_iso()`
(`scripts/check_proof_freshness.py:62-77`) formats an epoch by shelling
`git show -s --format=%cs @{<epoch>}`. `@{<epoch>}` is not an epoch formatter — it is
git's **reflog-relative revision syntax**, resolving to "whatever commit was HEAD at that
time on the current branch." Observed:

```
$ git show -s --format=%cs "@{1750000000}"
warning: log for 'main' only goes back to Fri, 26 Jun 2026 00:07:33 -0500
2026-06-25
```

Any epoch older than the reflog window clamps to the reflog's oldest entry. So the gate
printed `2026-06-25` for all five proofs whose **real** committer date is `2026-05-10`:

| Path | `git log -1 --format=%ct` | `--format=%cs` (truth) | Gate printed |
|---|---|---|---|
| `proofs/summary.md` | 1778447907 | **2026-05-10** | 2026-06-25 |
| `.gzkit/rules` | 1785323700 | **2026-07-29** | (not printed) |
| `src/gzkit/governance/trust_audits` | 1785565636 | **2026-08-01** | 2026-08-01 (coincidentally right — recent enough to be in the reflog) |

The comparison `proof_epoch < surface_epoch` (`:111`, `:113`) uses raw ints and is
correct, so the pass/fail verdict and exit 3 are trustworthy. Only the human-readable
labels — including the ones in the POLICY BREACH recovery prose — are wrong, and they
are wrong in the direction that makes stale evidence look ~6 weeks fresher than it is.

**Routing:** one-line fix (`datetime.fromtimestamp(epoch, UTC).date().isoformat()` — the
function's own fallback at `:75-77` is already correct; the `git show` attempt above it
is the bug). Outside this chore's audit-only scope (`scripts/` is not `proofs/`), so it
is recorded here rather than fixed. This also means **the chore brief's stated premise —
"proofs last committed 2026-06-25" — came from this defective display path**; the real
date is 2026-05-10, making the staleness ~12 weeks, not ~5.

Touching a file without redoing the analysis would restore the green-by-construction
gate this acceptance criterion replaced. That did not happen here: every parity row cites
both a rule line and a `module:line`, and 19 of 26 rule files plus the entire
`trust_audits/` package moved since the superseded artifacts were written.
